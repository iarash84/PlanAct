# گردش کار توسعهٔ <span dir="ltr">PlanAct</span>

## شاخه و درخواست ادغام

از <span dir="ltr">`master`</span> شاخه‌ای با پیشوند <span dir="ltr">`feature/`</span>، <span dir="ltr">`fix/`</span>، <span dir="ltr">`refactor/`</span> یا <span dir="ltr">`chore/`</span> بسازید؛ پیش از درخواست ادغام آن را با آخرین <span dir="ltr">`master`</span> همگام کنید. مقصد درخواست، <span dir="ltr">`master`</span> است و هدف، ریسک و آزمون‌ها باید روشن باشند. ادغام فشرده ترجیح دارد تا هر تغییر یک ثبت روشن داشته باشد؛ توسعهٔ مستقیم روی <span dir="ltr">`master`</span> انجام ندهید.

## قرارداد پذیرش و شواهد

[<span dir="ltr">PRD</span>](product/PRD.md) رفتار و آمادگی محصول و [<span dir="ltr">AGENTS</span>](../AGENTS.md) قواعد پیاده‌سازی را مشخص می‌کنند. پیش از تغییر معنادار، قرارداد کوتاه را در همان درخواست ادغام یا سند ارزیابی موجود ثبت و به‌روز کنید؛ سند موازی نسازید:

- نتیجهٔ کاربر، مسیر واقعی، پیش‌نیازها و محدودهٔ خارج از کار؛
- موفقیت قابل مشاهده، خطا، لغو، تلاش مجدد و اصلاح/بازگردانی؛
- دادهٔ پایدار و آثار راه‌اندازی مجدد، مهاجرت، پشتیبان/بازگردانی و پلتفرم؛
- مصرف‌کنندگان نیازمند بازخوانی و شاهد لازم برای هر ادعا.

مسیر اقدام کاربر ← فرمان ← قاعدهٔ دامنه ← نوشتن پایدار ← بازخوانی رابط ← مصرف‌کنندگان را دنبال کنید. کوچک‌ترین مسیر کامل مصوب را تحویل دهید. کار زیرساختی، قابلیت آمادهٔ کاربر نیست؛ پیش‌نیاز یا تصمیم نامشخص را اختراع نکنید و وضعیت ناقص را گزارش کنید. برای تغییر مستندات، سازگاری/اختلاف/پیوند کافی است؛ بازآرایی بدون تغییر رفتار به آزمون مرتبط نیاز دارد. این تناسب شرط امنیتی انتشار یا حفظ داده را حذف نمی‌کند.

پیش از ادغام، بازبین مستقل قرارداد، شواهد و مثال نقض را بررسی می‌کند. خودبازبینی جای بررسی مستقل نیست؛ عامل بازبین نیز مجوز انتشار مستقل نمی‌دهد. درخواست زیرساختی/ناقص تنها با ثبت محدودیت، مسئول و تصمیم عرضه قابل ادغام است و تضمین ضروری همان تغییر باید برقرار باشد. پذیرش درخواست مجوز انتشار کل برنامه نیست؛ مسئول انتشار همهٔ مسیرهای در دسترس و شرط‌های مشترک انتشار را بررسی می‌کند.

| معیار | شاهد و محیط | نتیجه | کمبود و تصمیم |
| --- | --- | --- | --- |
| نتیجهٔ قرارداد | دستور/مراحل، شناسهٔ ثبت و ساخت، تاریخ، دستگاه/سیستم‌عامل/حجم | موفق، ناموفق یا اجرا‌نشده؛ پیوند شاهد | مسئول، اقدام بعدی و تصمیم عرضه/انتشار |

شواهد تاریخی حذف نمی‌شوند؛ اعتبار آن‌ها برای نسخهٔ فعلی مشخص شود. گزارش پایان، پیاده‌سازی، راستی‌آزمایی، اجرا‌نشده‌ها و موانع انتشار را جدا می‌کند؛ نام بازبین و دامنهٔ پذیرفته‌شده ثبت شود.

آزمون دامنه محاسبه را ثابت می‌کند؛ ماندگاری به مخزن تولیدی و بستن و بازکردن دوبارهٔ پایگاه داده، رابط به مسیر ورود واقعی و بازخوانی و ادعای بومی به دستگاه نیاز دارد. شناسهٔ بسته، نسخه، نوع ساخت و تفاوت فایل آزمایشی/انتشار ثبت شوند. برای حجم/چیدمان، دادهٔ واقعی، بودجهٔ دستگاه مرجع، عرض باریک، متن بزرگ، راست‌به‌چپ و حالت‌های روشن و تیره بررسی شوند. رفع نقص مهم باید آزمون جلوگیری از تکرار خطا و یادداشت کوتاه معیار جاافتاده داشته باشد و به بازآرایی نامرتبط تبدیل نشود.

## نگهداری گزارش‌ها

خلاصه، دستور، محیط، تاریخ، شناسهٔ ثبت/ساخت و کمبود را در رکورد همان قابلیت نگه دارید. گزارش محلی در <span dir="ltr">`build/verification/`</span> است؛ خروجی خام همهٔ اجراها لازم نیست وارد گیت شود. ایجاد پوشه/هدایت خروجی اختیاری است و اسکریپت بررسی را تغییر نمی‌دهد.

برای <span dir="ltr">GitHub Actions</span> شناسهٔ اجرا/ثبت و گزارش/بستهٔ خروجی همان اجرا را ثبت کنید؛ انقضای بسته به معنی شاهد دائمی نیست. [شواهد تاریخی منتخب](verification/evidence/README.md) بازنویسی نمی‌شوند. شاهد خام جدید هدف مشخص، هویت اجرا و بررسی محتوای حساس می‌خواهد. گزارش موردارجاع هنگام پاک‌سازی بدون تغییر محتوا منتقل و پیوند اصلاح می‌شود؛ فقط خروجی موقت بی‌ارجاع حذف می‌شود. پیکربندی ساخت و فایل هش/منشأ انتشار گزارش موقت نیستند.

## بررسی محلی

پیش‌نیاز فعلی: <span dir="ltr">Flutter</span> <span dir="ltr">`3.47.5`</span>، <span dir="ltr">Dart</span> مطابق <span dir="ltr">`pubspec.yaml`</span>، <span dir="ltr">Java</span> <span dir="ltr">`17`</span> و <span dir="ltr">compile SDK</span> اندروید <span dir="ltr">`36`</span>.

### ویندوز

از ریشهٔ مخزن:

<div dir="ltr">

```powershell
.\tool\ci.ps1
```

</div>

اگر سیاست <span dir="ltr">PowerShell</span> مانع است، تغییر فقط برای همین فرایند:

<div dir="ltr">

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tool\ci.ps1
```

</div>

یا <span dir="ltr">PowerShell</span> 7:

<div dir="ltr">

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File .\tool\ci.ps1
```

</div>

برای بررسی بدون ساخت اندروید، مقدار قبلی متغیر را حفظ و سپس بازگردانید:

<div dir="ltr">

```powershell
$previousSkipAndroidBuild = $env:PLANACT_SKIP_ANDROID_BUILD
try {
    $env:PLANACT_SKIP_ANDROID_BUILD = 'true'
    .\tool\ci.ps1
} finally {
    if ($null -eq $previousSkipAndroidBuild) {
        Remove-Item Env:PLANACT_SKIP_ANDROID_BUILD -ErrorAction SilentlyContinue
    } else {
        $env:PLANACT_SKIP_ANDROID_BUILD = $previousSkipAndroidBuild
    }
}
```

</div>

این مسیر <span dir="ltr">CI</span> کامل نیست. اجرای کامل به امضای معتبر در <span dir="ltr">`android/key.properties`</span> یا متغیرهای <span dir="ltr">`ANDROID_KEYSTORE_PATH`</span>، <span dir="ltr">`ANDROID_KEYSTORE_PASSWORD`</span>، <span dir="ltr">`ANDROID_KEY_ALIAS`</span> و <span dir="ltr">`ANDROID_KEY_PASSWORD`</span> نیاز دارد؛ دستور اصلی را بدون <span dir="ltr">`PLANACT_SKIP_ANDROID_BUILD`</span> اجرا کنید.

### لینوکس و مک‌اواس

<div dir="ltr">

```bash
bash tool/ci.sh
```

</div>

هر دو اسکریپت فایل قفل را با <span dir="ltr">`flutter pub get --enforce-lockfile`</span>، تولید متن فارسی، قالب‌بندی، تحلیل و آزمون‌ها بررسی می‌کنند و پیش‌فرض ساخت انتشار اندروید دارند. <span dir="ltr">`PLANACT_SKIP_ANDROID_BUILD=true`</span> در <span dir="ltr">Bash</span> نیز بررسی ناقص است؛ اجرای دستی جداگانهٔ ساخت جای <span dir="ltr">CI</span> کامل نیست.

## <span dir="ltr">CI</span> و رفع شکست

<span dir="ltr">GitHub Actions</span> برای درخواست‌های مقصد <span dir="ltr">`master`</span> و ارسال‌های <span dir="ltr">`master`</span> اجرا می‌شود؛ اجرای قدیمی همان شاخه/درخواست لغو می‌شود. مراحل شامل وابستگی، منابع تولیدشده، قالب‌بندی، تحلیل، کل آزمون‌ها و ساخت سازگار انتشار اندروید است.

۱. گزارش همان مرحله را بخوانید و علت را اصلاح کنید.
۲. اسکریپت متناسب با سیستم‌عامل را محلی اجرا کنید.
۳. خطای موقت زیرساخت/شبکه را با گزینهٔ <span dir="ltr">`Re-run failed jobs`</span> تکرار کنید؛ ثبت بی‌معنی نسازید.
۴. اثر تغییر فایل قفل، مهاجرت یا امضا را در درخواست ادغام بنویسید.

## انتشار اندروید

سلامت فنی و آمادگی محصول دو دروازهٔ مستقل‌اند. موفقیت <span dir="ltr">CI</span> پذیرش محصول نیست؛ دامنهٔ انتشار همهٔ قابلیت‌های در دسترس و موانع قبلی را شامل می‌شود. پنهان‌کردن ورودی، دروازهٔ مشترک امنیت/ماندگاری/پلتفرم را معاف نمی‌کند.

طبق تصمیم نگه‌دارندهٔ تنها در <span dir="ltr">۲۰۲۶-۱۰-۱۳</span>، اجرای دستی مجوز خودکارسازی «ساخت نامزد انتشار ← بررسی فنی ← انتشار همان فایل‌ها بدون ساخت مجدد» است؛ محیط انتشار یا تأیید نفر دوم لازم نیست. این تصمیم شاهد مستقل یا دستگاه را انجام‌شده نمی‌کند. [گردش کار انتشار](../.github/workflows/release.yml) فایل‌ها، هش‌ها و هویت ثبت/اجرا را به بستهٔ کاندید می‌فرستد؛ پس از بررسی فنی همان فایل‌ها و برچسب متصل به همان ثبت منتشر می‌شوند.

خودکارسازی آمادگی محصول را اعمال نمی‌کند؛ مسئولیت با نگه‌دارنده است. معیار الزامی ناموفق/اجرا‌نشده یا مانع امنیت/داده/پلتفرم اجازهٔ ادعای آمادگی یا انتشار دامنهٔ متأثر نمی‌دهد. ناقص‌بودن نیازمند تصمیم عرضه و محدودیت روشن است؛ برچسب آزمایشی جای تضمین ضروری را نمی‌گیرد.

انتشار فقط از <span dir="ltr">`master`</span> و اجرای دستی **<span dir="ltr">Release Android</span>**:

1. نسخهٔ <span dir="ltr">`X.Y.Z+build`</span> را در <span dir="ltr">`pubspec.yaml`</span> تغییر و در <span dir="ltr">`master`</span> ادغام کنید؛ شواهد پذیرش را به ثبت ثابت و فایل کاندید متصل کنید.
2. در <span dir="ltr">GitHub</span> مسیر <span dir="ltr">`Actions → Release Android → Run workflow`</span> را باز کنید.
3. نسخه بدون <span dir="ltr">`v`</span> مانند <span dir="ltr">`0.1.16`</span> وارد شود؛ پس از موفقیت بررسی‌ها انتشار خودکار است.
4. نسخه و یادداشت متناسب بررسی، اعتبارسنجی مشترک اجرا و کلید تولید فقط در مرحلهٔ ساخت آماده می‌شود. <span dir="ltr">APK</span> امضاشده از نظر شناسهٔ بسته، نسخه، معماری و گواهی بررسی می‌شود.
5. هویت و هش دوباره بررسی و همان فایل بدون ساخت مجدد منتشر می‌شود؛ شکست مانع انتشار است. لغو پس از درخواست ایجاد انتشار ممکن است آن را باقی بگذارد؛ پیش از تلاش مجدد وضعیت را بررسی کنید. نسخهٔ موجود بازنویسی نمی‌شود.
6. ثبت، شناسهٔ اجرا، کد نسخه، گواهی و هش <span dir="ltr">APK</span> همراه شاهد دستگاه نگه داشته شود. کد نسخهٔ انتشار از شمارهٔ اجرای گردش کار است و باید از همهٔ <span dir="ltr">APK</span>های توزیع‌شده بیشتر باشد.

برچسب را دستی نسازید/ارسال نکنید. کلید خصوصی، مخزن کلید و <span dir="ltr">`android/key.properties`</span> وارد گیت نمی‌شوند. نسخهٔ هدف <span dir="ltr">`0.1.16+9`</span> و [یادداشت نسخه](releases/0.1.16.md) است؛ یادداشت با هش در کاندید می‌ماند و متن انتشار را تأمین می‌کند. آماده‌سازی فایل‌ها مجوز اجرای گردش کار یا ادعای آمادگی نیست.

مقادیر محرمانهٔ انتشار:

- <span dir="ltr">`ANDROID_KEYSTORE_BASE64`</span>
- <span dir="ltr">`ANDROID_KEYSTORE_PASSWORD`</span>
- <span dir="ltr">`ANDROID_KEY_ALIAS`</span>
- <span dir="ltr">`ANDROID_KEY_PASSWORD`</span>
- <span dir="ltr">`ANDROID_SIGNING_CERT_SHA256`</span>
- <span dir="ltr">`SYMBOLS_ENCRYPTION_PASSPHRASE`</span>

## تنظیمات دستی <span dir="ltr">GitHub</span>

نگه‌دارنده باید حفاظت شاخه/قواعد <span dir="ltr">`master`</span>، بررسی <span dir="ltr">CI</span> الزامی، درخواست ادغام و حل گفت‌وگوها، محدودیت ارسال مستقیم و ادغام فشرده را در تنظیمات فعال کند. برای نگه‌دارندهٔ تنها بازبینی نفر دوم شرط فنی نیست؛ مسئولیت پذیرش باقی است. اجرای انتشار فقط برای افراد مورداعتماد و مقادیر محرمانه در <span dir="ltr">`Settings → Secrets and variables → Actions`</span> مخزن باشد؛ گردش کار به مقادیر مخصوص محیط انتشار دسترسی ندارد. فایل‌های مخزن اعمال خودکار این تنظیمات را ادعا نمی‌کنند.
