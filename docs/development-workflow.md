# گردش کار توسعهٔ PlanAct

## شاخه و درخواست ادغام

از `master` شاخه‌ای با پیشوند `feature/`، `fix/`، `refactor/` یا `chore/` بسازید؛ پیش از درخواست ادغام آن را با آخرین `master` همگام کنید. مقصد درخواست، `master` است و هدف، ریسک و آزمون‌ها باید روشن باشند. ادغام فشرده ترجیح دارد تا هر تغییر یک ثبت روشن داشته باشد؛ توسعهٔ مستقیم روی `master` انجام ندهید.

## قرارداد پذیرش و شواهد

[PRD](product/PRD.md) رفتار و آمادگی محصول و [AGENTS](../AGENTS.md) قواعد پیاده‌سازی را مشخص می‌کنند. پیش از تغییر معنادار، قرارداد کوتاه را در همان درخواست ادغام یا سند ارزیابی موجود ثبت و به‌روز کنید؛ سند موازی نسازید:

- نتیجهٔ کاربر، مسیر واقعی، پیش‌نیازها و محدودهٔ خارج از کار؛
- موفقیت قابل مشاهده، خطا، لغو، تلاش مجدد و اصلاح/بازگردانی؛
- دادهٔ پایدار و آثار راه‌اندازی مجدد، مهاجرت، پشتیبان/بازگردانی و پلتفرم؛
- مصرف‌کنندگان نیازمند بازخوانی و شاهد لازم برای هر ادعا.

مسیر اقدام کاربر ← فرمان ← قاعدهٔ دامنه ← نوشتن پایدار ← بازخوانی رابط ← مصرف‌کنندگان را دنبال کنید. کوچک‌ترین مسیر کامل مصوب را تحویل دهید. کار زیرساختی، قابلیت آمادهٔ کاربر نیست؛ پیش‌نیاز یا تصمیم نامشخص را اختراع نکنید و وضعیت ناقص را گزارش کنید. برای تغییر مستندات، سازگاری/اختلاف/پیوند کافی است؛ بازآرایی بدون تغییر رفتار به آزمون مرتبط نیاز دارد. این تناسب دروازهٔ امنیت یا حفظ داده را حذف نمی‌کند.

پیش از ادغام، بازبین مستقل قرارداد، شواهد و مثال نقض را بررسی می‌کند. خودبازبینی جای بررسی مستقل نیست؛ عامل بازبین نیز مجوز انتشار مستقل نمی‌دهد. درخواست زیرساختی/ناقص تنها با ثبت محدودیت، مسئول و تصمیم عرضه قابل ادغام است و تضمین ضروری همان تغییر باید برقرار باشد. پذیرش درخواست مجوز انتشار کل برنامه نیست؛ مسئول انتشار همهٔ مسیرهای در دسترس و دروازه‌های مشترک را بررسی می‌کند.

| معیار | شاهد و محیط | نتیجه | کمبود و تصمیم |
| --- | --- | --- | --- |
| نتیجهٔ قرارداد | دستور/مراحل، شناسهٔ ثبت و ساخت، تاریخ، دستگاه/سیستم‌عامل/حجم | موفق، ناموفق یا اجرا‌نشده؛ پیوند شاهد | مسئول، اقدام بعدی و تصمیم عرضه/انتشار |

شواهد تاریخی حذف نمی‌شوند؛ اعتبار آن‌ها برای نسخهٔ فعلی مشخص شود. گزارش پایان، پیاده‌سازی، راستی‌آزمایی، اجرا‌نشده‌ها و موانع انتشار را جدا می‌کند؛ نام بازبین و دامنهٔ پذیرفته‌شده ثبت شود.

آزمون دامنه محاسبه را ثابت می‌کند؛ ماندگاری به مخزن تولیدی و بازگشایی سرد، رابط به مسیر ورود واقعی و بازخوانی و ادعای بومی به دستگاه نیاز دارد. شناسهٔ بسته، نسخه، نوع ساخت و تفاوت فایل آزمایشی/انتشار ثبت شوند. برای حجم/چیدمان، دادهٔ واقعی، بودجهٔ دستگاه مرجع، عرض باریک، متن بزرگ، RTL و دو تم بررسی شوند. رفع نقص مهم باید آزمون بازگشت نقص و یادداشت کوتاه معیار جاافتاده داشته باشد و به بازآرایی نامرتبط تبدیل نشود.

## نگهداری گزارش‌ها

خلاصه، دستور، محیط، تاریخ، شناسهٔ ثبت/ساخت و کمبود را در رکورد همان قابلیت نگه دارید. گزارش محلی در `build/verification/` است؛ خروجی خام همهٔ اجراها لازم نیست وارد گیت شود. ایجاد پوشه/هدایت خروجی اختیاری است و اسکریپت بررسی را تغییر نمی‌دهد.

برای GitHub Actions شناسهٔ اجرا/ثبت و گزارش/بستهٔ خروجی همان اجرا را ثبت کنید؛ انقضای بسته به معنی شاهد دائمی نیست. [شواهد تاریخی منتخب](verification/evidence/README.md) بازنویسی نمی‌شوند. شاهد خام جدید هدف مشخص، هویت اجرا و بررسی محتوای حساس می‌خواهد. گزارش موردارجاع هنگام پاک‌سازی بدون تغییر محتوا منتقل و پیوند اصلاح می‌شود؛ فقط خروجی موقت بی‌ارجاع حذف می‌شود. پیکربندی ساخت و فایل هش/منشأ انتشار گزارش موقت نیستند.

## بررسی محلی

پیش‌نیاز فعلی: Flutter `3.47.5`، Dart مطابق `pubspec.yaml`، Java `17` و compile SDK اندروید `36`.

### ویندوز

از ریشهٔ مخزن:

```powershell
.\tool\ci.ps1
```

اگر سیاست PowerShell مانع است، تغییر فقط برای همین فرایند:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tool\ci.ps1
```

یا PowerShell 7:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File .\tool\ci.ps1
```

برای بررسی بدون ساخت اندروید، مقدار قبلی متغیر را حفظ و سپس بازگردانید:

```powershell
$previousSkipAndroidBuild = $env:PLANACT_SKIP_ANDROID_BUILD
try {
    $env:PLANACT_SKIP_ANDROID_BUILD = 'true'
    .\tool\ci.ps1
} finally {
    if ($null -eq $previousSkipAndroidBuild) {
        Remove-Item Env:PLANACT_SKIP_ANDROID_BUILD -ErrorAction SilentlyContinue
    } else {
        $env:PLANACT_SKIP_ANDROID_BUILD = $previousSkipAndroidBuild
    }
}
```

این مسیر CI کامل نیست. اجرای کامل به امضای معتبر در `android/key.properties` یا متغیرهای `ANDROID_KEYSTORE_PATH`، `ANDROID_KEYSTORE_PASSWORD`، `ANDROID_KEY_ALIAS` و `ANDROID_KEY_PASSWORD` نیاز دارد؛ دستور اصلی را بدون `PLANACT_SKIP_ANDROID_BUILD` اجرا کنید.

### لینوکس و مک‌اواس

```bash
bash tool/ci.sh
```

هر دو اسکریپت فایل قفل را با `flutter pub get --enforce-lockfile`، تولید متن فارسی، قالب‌بندی، تحلیل و آزمون‌ها بررسی می‌کنند و پیش‌فرض ساخت انتشار اندروید دارند. `PLANACT_SKIP_ANDROID_BUILD=true` در Bash نیز بررسی ناقص است؛ اجرای دستی جداگانهٔ ساخت جای CI کامل نیست.

## CI و رفع شکست

GitHub Actions برای درخواست‌های مقصد `master` و ارسال‌های `master` اجرا می‌شود؛ اجرای قدیمی همان شاخه/درخواست لغو می‌شود. مراحل شامل وابستگی، منابع تولیدشده، قالب‌بندی، تحلیل، کل آزمون‌ها و ساخت سازگار انتشار اندروید است.

۱. گزارش همان مرحله را بخوانید و علت را اصلاح کنید.
۲. اسکریپت متناسب با سیستم‌عامل را محلی اجرا کنید.
۳. خطای موقت زیرساخت/شبکه را با گزینهٔ `Re-run failed jobs` تکرار کنید؛ ثبت بی‌معنی نسازید.
۴. اثر تغییر فایل قفل، مهاجرت یا امضا را در درخواست ادغام بنویسید.

## انتشار اندروید

سلامت فنی و آمادگی محصول دو دروازهٔ مستقل‌اند. موفقیت CI پذیرش محصول نیست؛ دامنهٔ انتشار همهٔ قابلیت‌های در دسترس و موانع قبلی را شامل می‌شود. پنهان‌کردن ورودی، دروازهٔ مشترک امنیت/ماندگاری/پلتفرم را معاف نمی‌کند.

طبق تصمیم نگه‌دارندهٔ تنها در ۲۰۲۶-۱۰-۱۳، اجرای دستی مجوز خودکارسازی «ساخت کاندید ← بررسی فنی ← انتشار همان فایل‌ها بدون ساخت مجدد» است؛ محیط انتشار یا تأیید نفر دوم لازم نیست. این تصمیم شاهد مستقل یا دستگاه را انجام‌شده نمی‌کند. [گردش کار انتشار](../.github/workflows/release.yml) فایل‌ها، هش‌ها و هویت ثبت/اجرا را به بستهٔ کاندید می‌فرستد؛ پس از بررسی فنی همان فایل‌ها و برچسب متصل به همان ثبت منتشر می‌شوند.

خودکارسازی آمادگی محصول را اعمال نمی‌کند؛ مسئولیت با نگه‌دارنده است. معیار الزامی ناموفق/اجرا‌نشده یا مانع امنیت/داده/پلتفرم اجازهٔ ادعای آمادگی یا انتشار دامنهٔ متأثر نمی‌دهد. ناقص‌بودن نیازمند تصمیم عرضه و محدودیت روشن است؛ برچسب آزمایشی جای تضمین ضروری را نمی‌گیرد.

انتشار فقط از `master` و اجرای دستی **Release Android**:

1. نسخهٔ `X.Y.Z+build` را در `pubspec.yaml` تغییر و در `master` ادغام کنید؛ شواهد پذیرش را به ثبت ثابت و فایل کاندید متصل کنید.
2. در GitHub مسیر `Actions → Release Android → Run workflow` را باز کنید.
3. نسخه بدون `v` مانند `0.1.16` وارد شود؛ پس از موفقیت بررسی‌ها انتشار خودکار است.
4. نسخه و یادداشت متناسب بررسی، اعتبارسنجی مشترک اجرا و کلید تولید فقط در مرحلهٔ ساخت آماده می‌شود. APK امضاشده از نظر شناسهٔ بسته، نسخه، معماری و گواهی بررسی می‌شود.
5. هویت و هش دوباره بررسی و همان فایل بدون ساخت مجدد منتشر می‌شود؛ شکست مانع انتشار است. لغو پس از درخواست ایجاد انتشار ممکن است آن را باقی بگذارد؛ پیش از تلاش مجدد وضعیت را بررسی کنید. نسخهٔ موجود بازنویسی نمی‌شود.
6. ثبت، شناسهٔ اجرا، کد نسخه، گواهی و هش APK همراه شاهد دستگاه نگه داشته شود. کد نسخهٔ انتشار از شمارهٔ اجرای گردش کار است و باید از همهٔ APKهای توزیع‌شده بیشتر باشد.

برچسب را دستی نسازید/ارسال نکنید. کلید خصوصی، مخزن کلید و `android/key.properties` وارد گیت نمی‌شوند. نسخهٔ هدف `0.1.16+9` و [یادداشت نسخه](releases/0.1.16.md) است؛ یادداشت با هش در کاندید می‌ماند و متن انتشار را تأمین می‌کند. آماده‌سازی فایل‌ها مجوز اجرای گردش کار یا ادعای آمادگی نیست.

مقادیر محرمانهٔ انتشار:

- `ANDROID_KEYSTORE_BASE64`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`
- `ANDROID_SIGNING_CERT_SHA256`
- `SYMBOLS_ENCRYPTION_PASSPHRASE`

## تنظیمات دستی GitHub

نگه‌دارنده باید حفاظت شاخه/قواعد `master`، بررسی CI الزامی، درخواست ادغام و حل گفت‌وگوها، محدودیت ارسال مستقیم و ادغام فشرده را در تنظیمات فعال کند. برای نگه‌دارندهٔ تنها بازبینی نفر دوم شرط فنی نیست؛ مسئولیت پذیرش باقی است. اجرای انتشار فقط برای افراد مورداعتماد و مقادیر محرمانه در `Settings → Secrets and variables → Actions` مخزن باشد؛ گردش کار به مقادیر مخصوص محیط انتشار دسترسی ندارد. فایل‌های مخزن اعمال خودکار این تنظیمات را ادعا نمی‌کنند.

## همگام‌سازی و بازگشت

پیش از کار جدید:

```bash
git fetch origin
git switch master
git pull --ff-only origin master
git switch -c feature/short-description
```

پیش از درخواست ادغام:

```bash
git fetch origin
git rebase origin/master
```

سپس اسکریپت محلی بالا را اجرا کنید. تغییر منتشرنشده را در همان شاخه اصلاح کنید؛ تاریخچه، دفتر مالی، رخداد حل‌شده و پشتیبان را برای ساده‌سازی حذف نکنید.
