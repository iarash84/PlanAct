# راهنمای دریافت، راه‌اندازی، ساخت و توسعهٔ <span dir="ltr">PlanAct</span>

این راهنما برای کسی است که هنوز Git، Flutter یا ابزارهای اندروید را نصب نکرده است. هدف بخش‌های آغازین، دریافت کد و ساخت یک فایل نصب آزمایشی اندروید است؛ برای این کار به حساب ابری برنامه، سرور، Android Studio یا کلید انتشار نگه‌دارنده نیاز ندارید. اتصال اینترنت برای دریافت ابزارها و وابستگی‌های اولین ساخت لازم است؛ محلی‌بودن برنامه به معنی بی‌نیازی محیط ساخت از اینترنت نیست.

**دامنهٔ راهنما:** خروجی اندروید روی ویندوز، لینوکس و macOS. مسیر اصلی و جزئیات تصویریِ منوها برای ویندوز است؛ فرمان‌های جایگزین دو سیستم دیگر نیز آمده‌اند. این مخزن را برای ساخت وب، iOS یا برنامهٔ دسکتاپ آماده فرض نکنید. نام منوهای ابزارها ممکن است بین نسخه‌ها کمی متفاوت باشد.

## نقشهٔ راه برای اولین ساخت

۱. بخش «مفاهیم و ابزارها» را بخوانید و Git و Flutter را نصب کنید.
۲. **فقط یکی** از دو مسیر «با Android Studio» یا «بدون Android Studio» را برای ابزارهای اندروید انجام دهید.
۳. کد را از Git بگیرید و وابستگی‌ها را دریافت کنید.
۴. فایل نصب آزمایشی بسازید؛ داشتن گوشی یا شبیه‌ساز برای **ساخت فایل** لازم نیست.
۵. در صورت تمایل، آن را روی گوشی آزمایشی یا شبیه‌ساز اجرا کنید.
۶. فقط برای مشارکت در توسعه یا ساخت انتشار، بخش‌های بعدی را ادامه دهید.

## مفاهیم و ابزارها

### چند اصطلاح ضروری

- **کد منبع / مخزن:** فایل‌های سازندهٔ برنامه و تاریخچهٔ تغییرات آن‌ها؛ Git آن‌ها را دریافت و مدیریت می‌کند و GitHub میزبان آنلاین آن‌هاست.
- **ترمینال:** پنجره‌ای برای نوشتن فرمان. پس از نوشتن هر فرمان Enter بزنید و تا پایان آن صبر کنید. خروجیِ نمونه را دوباره به‌عنوان فرمان اجرا نکنید.
- **پوشهٔ جاری:** پوشه‌ای که ترمینال اکنون در آن قرار دارد. فرمان تغییر پوشه در مثال‌ها آمده است. «ریشهٔ مخزن» پوشه‌ای است که [فایل تعریف پروژه](../pubspec.yaml) داخل آن است، نه پوشهٔ اندروید.
- **SDK:** مجموعه ابزار توسعه. Flutter SDK ابزار ساخت برنامه را دارد؛ Android SDK ابزار ساخت و ارتباط با اندروید را فراهم می‌کند.
- **JDK:** ابزارهای Java برای اجرای بخش اندرویدی فرایند ساخت؛ نصب فقط JRE کافی نیست.
- **بیلد:** تبدیل کد به فایل اجرایی. APK فایل نصب مستقیم اندروید است؛ AAB بستهٔ توزیع برای فروشگاه است و مستقیماً مانند APK نصب نمی‌شود.
- **Debug و Release:** اولی برای توسعه و عیب‌یابی و دومی برای ساخت بهینه و امضاشده است. ساخت موفق هیچ‌کدام به‌تنهایی آمادگی محصول برای انتشار را ثابت نمی‌کند.
- **متغیر محیطی و Path:** تنظیمات سیستم برای معرفی محل ابزارها. Path فهرست پوشه‌هایی است که سیستم برای یافتن فرمان‌ها جست‌وجو می‌کند؛ مسیرهای قبلی آن را پاک نکنید.

| افزونه‌های Flutter و Dart | فقط برای تجربهٔ توسعه در ویرایشگر | در Android Studio افزونهٔ Flutter را نصب و پیشنهاد نصب Dart را قبول کنید |
| Visual Studio Code | اختیاری در مسیر بدون Android Studio | [دریافت رسمی](https://code.visualstudio.com/)؛ افزونهٔ Flutter از ناشر Dart Code، همراه Dart |

**نیازی به نصب مستقل Gradle، Kotlin، SQLite Server، Node.js، Python، Docker، Firebase یا Visual Studio کامل برای این مسیر اندروید ندارید.** Gradle Wrapper پروژه نسخهٔ لازم را دریافت می‌کند. Visual Studio با Visual Studio Code فرق دارد؛ هشدار Flutter دربارهٔ ابزار دسکتاپ ویندوز مانع ساخت اندروید نیست. حساب Google نیز برای ساخت APK محلی لازم نیست؛ دریافت کد عمومی با HTTPS معمولاً بدون حساب GitHub انجام می‌شود، اما برای مخزن خصوصی باید دسترسی داشته باشید.

### نسخه‌های مرجع این مخزن

در زمان به‌روزرسانی این راهنما، گردش کار خودکار از **Flutter 3.47.5** و **Java 17** استفاده می‌کند؛ قید Dart پروژه **^3.13.4** است و باید با Dart همراه همان Flutter تأمین شود. نسخهٔ کامپایل اندروید **36**، Android Gradle Plugin برابر **9.0.1** و Gradle Wrapper برابر **9.1.0** است. نسخهٔ حداقل و هدف اندروید و NDK از Flutter خوانده می‌شوند؛ عدد مربوط به تولید آیکون، حداقل نسخهٔ واقعی برنامه نیست.

منابع تطبیق نسخه‌ها: [گردش کار بررسی](../.github/workflows/ci.yml)، [تعریف پروژه](../pubspec.yaml)، [پیکربندی برنامهٔ اندروید](../android/app/build.gradle.kts)، [افزونه‌های اندروید](../android/settings.gradle.kts) و [Gradle Wrapper](../android/gradle/wrapper/gradle-wrapper.properties). اگر نسخهٔ Flutter موردنظر در آرشیو رسمی پیدا نشد، با نگه‌دارنده نسخهٔ ثبت‌شده در گردش کار را تطبیق دهید؛ با نصب نسخهٔ تصادفی یا تغییر قید Dart، ناسازگاری را پنهان نکنید.

### سیستم مناسب و اینترنت

- برای مسیر ویندوز، ویندوز ۱۰/۱۱ نسخهٔ ۶۴بیتی و دسترسی نصب برنامه‌ها داشته باشید. بسته‌های x64 و ARM64 را با معماری سیستم خود اشتباه نگیرید؛ پشتیبانی ابزار انتخاب‌شده از معماری میزبان را در صفحهٔ رسمی بررسی کنید.
- برای برنامه‌ریزی عملی، ۱۶ گیگابایت RAM و دست‌کم ۳۰ گیگابایت فضای آزاد پیشنهاد می‌شود، نه به‌عنوان حداقل تضمین‌شدهٔ پروژه. شبیه‌ساز و چند System Image فضای بیشتری می‌خواهند. با RAM کمتر، گوشی واقعی و بستن برنامه‌های اضافی مناسب‌تر است.
- GitHub، مخازن Flutter/Dart، Google Maven، Maven Central، مخزن Gradle و سرور دریافت Android SDK باید در دسترس باشند. دریافت اولیه ممکن است طولانی باشد. بی‌حرکت‌بودن درصد برای چند لحظه لزوماً توقف نیست.
- در شبکهٔ محدود از مسیر دسترسی یا پراکسی مورداعتماد و مجاز استفاده کنید. اعتبارسنجی TLS را خاموش نکنید و وابستگی یا کلید را از کانال ناشناس نگیرید. تنظیم پراکسی مرورگر الزاماً به Git، Java و Flutter منتقل نمی‌شود.
- مسیر کوتاه و قابل‌نوشتن، بدون فاصله و حروف فارسی انتخاب کنید؛ نمونه‌های ویندوز این راهنما از پوشه‌های زیر در درایو C استفاده می‌کنند. اگر اجازهٔ نوشتن در آن‌ها ندارید، مسیر دیگری انتخاب و در **تمام** فرمان‌ها جایگزین کنید.

## نصب مشترک: ترمینال، Git و Flutter

### ۱. بازکردن ترمینال درست در ویندوز

از منوی Start، **Windows PowerShell** را باز کنید. فرمان‌های دارای برچسب powershell این راهنما برای همین محیط هستند؛ آن‌ها را در Command Prompt یا Git Bash نچسبانید. اجرای روزمرهٔ ساخت نباید با دسترسی Administrator باشد؛ فقط نصب برنامه یا فعال‌کردن امکانات سیستم ممکن است آن دسترسی را بخواهد.

برای دیدن پوشهٔ جاری و فایل‌هایش:

<div dir="ltr">

```powershell
Get-Location
Get-ChildItem
```

</div>

فرمان‌ها را خط‌به‌خط اجرا کنید؛ اگر خطی خطا داد، اول همان خطا را رفع کنید. بلوک‌های جدا معمولاً ادامهٔ یکدیگرند، مگر صریحاً نوشته شده باشد که باید روش دیگری را انتخاب کنید.

### ۲. نصب Git

نصب‌کنندهٔ رسمی را اجرا کنید. گزینهٔ استفاده از Git در خط فرمان و برنامه‌های دیگر را نگه دارید؛ معمولاً با عنوان **Git from the command line and also from 3rd-party software** دیده می‌شود. گزینه‌های پیش‌فرض دیگر برای شروع کافی‌اند. پس از نصب، ترمینال را ببندید و دوباره باز کنید:

<div dir="ltr">

```powershell
git --version
```

</div>

باید شمارهٔ نسخه چاپ شود. اگر فرمان شناخته نشد، نصب و Path را بررسی کنید؛ هنوز به مرحلهٔ بعد نروید.

### ۳. نصب Flutter با نسخهٔ پروژه

۱. از آرشیو رسمی، بستهٔ **Flutter 3.47.5** متناسب با سیستم‌عامل و معماری خود را دریافت کنید.
۲. در ویندوز ZIP را Extract All کنید؛ نتیجه باید شامل پوشهٔ Flutter با زیرپوشهٔ bin باشد. پوشه را طوری قرار دهید که مسیر ابزار همان مسیر مثال زیر شود. آن را داخل Program Files، پوشهٔ نیازمند مجوز مدیر یا پوشهٔ همگام‌شوندهٔ ابری نصب نکنید.
۳. در Start عبارت **Edit environment variables for your account** را جست‌وجو کنید؛ در بخش User variables، مقدار **Path → Edit → New** را باز کنید و مسیر زیر را به‌عنوان **یک ردیف جدید** اضافه کنید. Path موجود را جایگزین نکنید:

<div dir="ltr">

```text
C:\dev\flutter\bin
```

</div>

۴. پنجره‌ها را با OK ببندید؛ ترمینال و در صورت بازبودن، ویرایشگر را کاملاً ببندید و دوباره باز کنید.
۵. فرمان‌های زیر را اجرا کنید:

<div dir="ltr">

```powershell
where.exe flutter
where.exe dart
flutter --version
dart --version
flutter doctor -v
```

</div>

اولین مسیرهای دو فرمان نخست باید به همین Flutter برسند و شمارهٔ Flutter باید با نسخهٔ مرجع برابر باشد. اجرای اول ممکن است ابزارهای داخلی را دانلود کند. خطاهای بخش Android toolchain در این مرحله طبیعی‌اند و با یکی از دو مسیر بعد رفع می‌شوند. **برای این پروژه فرمان ارتقای Flutter را اجرا نکنید**؛ ارتقای ابزار باید تصمیم جداگانه و هماهنگ با CI باشد.

## مسیر اول: نصب ابزارهای اندروید با Android Studio

### ۱. نصب برنامه و SDK

۱. Android Studio را از منبع رسمی نصب کنید و در اجرای اول Setup Wizard را کامل کنید. اگر SDK یا Emulator پیشنهاد شد، SDK را نصب کنید؛ شبیه‌ساز فقط در صورت نیاز است.
۲. در صفحهٔ آغاز **More Actions → SDK Manager** را باز کنید؛ در پروژهٔ باز معمولاً از **Tools → SDK Manager** یا تنظیمات **Languages & Frameworks → Android SDK** در دسترس است.
۳. مسیر **Android SDK Location** را یادداشت کنید. معمولاً زیر پوشهٔ کاربر ویندوز و در مسیر AppData/Local/Android/Sdk است؛ مسیر واقعیِ نمایش‌داده‌شده ملاک است.
۴. در **SDK Platforms**، گزینهٔ **Android API 36 / Android 16** را انتخاب کنید. برای کامپایل، SDK Platform لازم است، نه فقط System Image.
۵. در **SDK Tools**، موارد **Android SDK Command-line Tools (latest)** و **Android SDK Platform-Tools** را نصب کنید. با **Show Package Details**، نسخهٔ **36.0.0** از **Android SDK Build-Tools** را هم انتخاب کنید. برای شبیه‌ساز، Android Emulator را نیز نصب کنید.
۶. Apply و تأیید مجوزها را بزنید و تا پایان دانلود صبر کنید. NDK موردنیاز Flutter/افزونه‌ها ممکن است در اولین ساخت به‌طور خودکار نصب شود؛ اگر ساخت شمارهٔ مشخصی خواست، همان نسخه را از **NDK (Side by side)** انتخاب کنید، نه یک نسخهٔ دلخواه.

### ۲. نصب و معرفی Java 17

برای اینکه ساخت ترمینال و CI از Java یکسان استفاده کنند، **JDK 17** را جداگانه نصب کنید؛ جدیدترین Android Studio ممکن است Java دیگری همراه داشته باشد. هنگام نصب Temurin، اگر گزینه‌های **Set JAVA_HOME** و **Add to PATH** وجود داشت، فعالشان کنید.

پس از نصب، در همان پنجرهٔ متغیرهای محیطی کاربر، مقدار **JAVA_HOME** را به پوشهٔ نصب JDK بدهید، نه زیرپوشهٔ bin. مثال زیر را با مسیر واقعی خود عوض کنید:

<div dir="ltr">

```text
C:\Program Files\Eclipse Adoptium\jdk-17.0.x-hotspot
```

</div>

این مثال نام واقعی نسخه نیست؛ از File Explorer پوشهٔ نصب را پیدا کنید. یک ردیف **%JAVA_HOME%\bin** نیز به Path اضافه کنید. ترمینال تازه باز کنید و سپس:

<div dir="ltr">

```powershell
java -version
javac -version
flutter config --jdk-dir "$env:JAVA_HOME"
flutter config --android-sdk "$env:LOCALAPPDATA\Android\Sdk"
flutter doctor --android-licenses
flutter doctor -v
```

</div>

فرمان معرفی SDK فقط وقتی درست است که SDK Manager همان مسیر پیش‌فرض را نشان داده باشد؛ در غیر این صورت مسیر واقعی را داخل گیومه بگذارید. خروجی Java و javac باید 17 باشد. متن هر مجوز را بخوانید و در صورت موافقت پاسخ y بدهید. در گزارش doctor، **Android toolchain** باید موفق باشد؛ هشدار نبود دستگاه تا زمان اتصال گوشی طبیعی است. اگر داخل Android Studio هم Gradle را اجرا می‌کنید، در **Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK** همان JDK 17 را انتخاب کنید؛ تنظیم Flutter لزوماً تنظیم داخلی IDE را عوض نمی‌کند.

### ۳. آماده‌کردن ویرایشگر

در **Settings → Plugins → Marketplace** افزونهٔ **Flutter** را نصب کنید؛ نصب وابستگی **Dart** را بپذیرید و در صورت درخواست برنامه را دوباره باز کنید. این افزونه‌ها جای Flutter SDK را نمی‌گیرند. اگر مسیر SDK پرسیده شد، پوشهٔ اصلی Flutter را بدهید، نه زیرپوشهٔ bin.

اکنون به بخش [دریافت پروژه](#clone-project) بروید؛ لازم نیست مسیر بدون Android Studio را هم انجام دهید.

<a id="without-studio"></a>

## مسیر دوم: ابزارهای اندروید بدون نصب Android Studio

در این مسیر یک ترمینال، Git، Flutter، JDK و Android SDK کافی است. VS Code اختیاری است و تمام فرمان‌های ساخت بدون هیچ ویرایشگری هم کار می‌کنند.

### ۱. نصب Java

JDK 17 را از Temurin نصب کنید و متغیر **JAVA_HOME** و Path را دقیقاً مانند بخش Java در مسیر اول تنظیم کنید. در ترمینال تازه، دو فرمان زیر باید نسخهٔ 17 بدهند:

<div dir="ltr">

```powershell
java -version
javac -version
flutter config --jdk-dir "$env:JAVA_HOME"
```

</div>

### ۲. چیدن درست Command-line Tools

۱. از صفحهٔ رسمی Android Studio، بخش **Command line tools only**، ZIP مخصوص ویندوز را بگیرید؛ لازم نیست نصب‌کنندهٔ خود Android Studio را دریافت کنید.
۲. با File Explorer پوشهٔ مقصد SDK و زیرپوشه‌های زیر را بسازید.
۳. محتویات پوشهٔ cmdline-tools داخل ZIP را در پوشهٔ latest قرار دهید. در پایان فایل اجرایی باید دقیقاً در مسیر زیر باشد؛ اگر دو پوشهٔ cmdline-tools پشت‌سرهم می‌بینید، ساختار را اصلاح کنید:

<div dir="ltr">

```text
C:\Android\Sdk\cmdline-tools\latest\bin\sdkmanager.bat
C:\Android\Sdk\cmdline-tools\latest\lib\
C:\Android\Sdk\cmdline-tools\latest\source.properties
```

</div>

### ۳. معرفی مسیرها و نصب اجزای SDK

از تنظیمات متغیرهای محیطی کاربر ویندوز، یک متغیر **ANDROID_HOME** با مقدار ریشهٔ SDK بسازید و این دو ردیف را به Path اضافه کنید:

<div dir="ltr">

```text
ANDROID_HOME = C:\Android\Sdk

%ANDROID_HOME%\cmdline-tools\latest\bin
%ANDROID_HOME%\platform-tools
```

</div>

سطر اول نشان‌دهندهٔ «نام = مقدار» در پنجرهٔ تنظیمات است و فرمان قابل اجرا نیست. متغیر قدیمی **ANDROID_SDK_ROOT** لازم نیست؛ اگر قبلاً وجود دارد نباید با ANDROID_HOME به دو SDK متفاوت اشاره کند.

ترمینال تازه باز کنید و خط‌به‌خط اجرا کنید:

<div dir="ltr">

```powershell
sdkmanager.bat --version
sdkmanager.bat --sdk_root="$env:ANDROID_HOME" --licenses
sdkmanager.bat --sdk_root="$env:ANDROID_HOME" "platform-tools" "platforms;android-36" "build-tools;36.0.0"
flutter config --android-sdk "$env:ANDROID_HOME"
flutter doctor --android-licenses
flutter doctor -v
adb version
```

</div>

مجوزها را بخوانید و در صورت موافقت قبول کنید. اولین ساخت ممکن است NDK یا CMake لازم را هم دانلود کند؛ اینترنت و فضای کافی و دسترسی نوشتن در SDK را حفظ کنید. اگر دانلود خودکار انجام نشد، شمارهٔ دقیق بسته را از خطای ساخت بخوانید و با sdkmanager نصب کنید. برای مثال، الگوی بستهٔ NDK برابر **ndk;شمارهٔ‌دقیق‌درخواستی** است؛ متن فارسیِ این الگو را عیناً اجرا نکنید. فهرست بسته‌ها با فرمان زیر دیده می‌شود:

<div dir="ltr">

```powershell
sdkmanager.bat --sdk_root="$env:ANDROID_HOME" --list
```

</div>

در این مسیر هشدار **Android Studio not installed** به‌تنهایی اشکال نیست؛ معیار، سلامت Android toolchain و موفقیت ساخت است. اگر فقط گوشی واقعی می‌خواهید، به Emulator یا System Image نیاز ندارید.

<a id="other-hosts"></a>

## تفاوت‌های نصب روی لینوکس و macOS

مراحل دریافت پروژه، وابستگی‌ها و فرمان‌های Flutter در ادامه مشترک‌اند. مثال‌های این بخش برای Bash/Zsh هستند؛ آن‌ها را در PowerShell اجرا نکنید.

۱. **Git:** در macOS نصب Git یا Command Line Tools اپل را از مسیر رسمی انجام دهید؛ اجرای فرمان زیر نصب ابزارهای اپل را پیشنهاد می‌کند. Xcode کامل برای خروجی اندروید لازم نیست. در Ubuntu/Debian فرمان نصب بسته‌ها را اجرا کنید؛ نام بسته‌ها در توزیع‌های دیگر متفاوت است:

<div dir="ltr">

```bash
# macOS
xcode-select --install
```

```bash
# Ubuntu / Debian
sudo apt update
sudo apt install git curl unzip xz-utils zip libglu1-mesa openjdk-17-jdk
```

</div>

۲. **Flutter:** آرشیو همان نسخه را متناسب با Linux یا macOS و معماری CPU بگیرید و در پوشهٔ قابل‌نوشتن استخراج کنید. برای Apple Silicon بستهٔ arm64 را انتخاب کنید؛ اگر ابزار مشخصی Rosetta خواست، از راهنمای رسمی همان ابزار پیروی کنید. مثال مسیرها در ادامه فرض می‌کند پوشهٔ Flutter در کنار پوشهٔ Android در پوشهٔ شخصی شماست؛ نام کاربری نمونه را جایگزین کنید.

۳. **Java:** در macOS، JDK 17 مخصوص معماری دستگاه را نصب کنید. در لینوکس مسیر واقعی نصب JDK را پیدا کنید؛ روی Ubuntu x64 معمولاً مسیر مثال زیر است ولی روی ARM متفاوت است.

۴. **Android SDK:** با Android Studio همان اجزای مسیر اول را نصب کنید؛ یا ZIP ابزار خط فرمان متناسب با میزبان را بگیرید و با همان ساختار latest مسیر دوم بچینید. در macOS معمولاً SDK ساخته‌شده توسط Studio در Library/Android/sdk زیر پوشهٔ کاربر و در Linux معمولاً Android/Sdk است. **مسیر واقعی خود را انتخاب کنید**؛ مثال زیر برای نصب دستی است.

۵. برای ماندگاری تنظیمات، خطوط متناسب با سیستم خود را به انتهای فایل تنظیمات شل کاربر اضافه کنید: [قواعد فایل‌های Zsh](https://zsh.sourceforge.io/Doc/Release/Files.html) و [قواعد فایل‌های Bash](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html) مرجع‌اند. برای Zsh معمول macOS و Bash تعاملی Linux، به‌ترتیب مسیرهای نمونهٔ زیر را در نظر بگیرید؛ نام کاربر را عوض کنید. اگر فایل موجود نیست، آن را با همین نام در پوشهٔ کاربر بسازید. این فایل‌ها مخفی‌اند؛ از ویرایشگر با نمایش فایل‌های مخفی استفاده کنید. سپس ترمینال را دوباره باز کنید. خطوط بعدی را نخست با مسیر واقعی خود جایگزین کنید:

<div dir="ltr">

```text
/Users/yourname/.zshrc
/home/yourname/.bashrc
```

</div>

<div dir="ltr">

```bash
# macOS: replace yourname with your actual account name
export FLUTTER_ROOT="/Users/yourname/development/flutter"
export ANDROID_HOME="/Users/yourname/Android/Sdk"
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"
export PATH="$FLUTTER_ROOT/bin:$JAVA_HOME/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH"
```

```bash
# Linux: replace yourname and verify the JDK path for your architecture
export FLUTTER_ROOT="/home/yourname/development/flutter"
export ANDROID_HOME="/home/yourname/Android/Sdk"
export JAVA_HOME="/usr/lib/jvm/java-17-openjdk-amd64"
export PATH="$FLUTTER_ROOT/bin:$JAVA_HOME/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH"
```

</div>

اگر با Studio نصب کرده‌اید، مقدار SDK بالا را با مسیر SDK Manager یکسان کنید. در نصب دستی، اگر اجرای sdkmanager با خطای مجوز اجرا روبه‌رو شد، مجوز فایل ابزار را بررسی کنید و فقط برای فایل مربوط مجوز اجرا بدهید؛ روی کل SDK مجوز همگانی نوشتن نگذارید.

<div dir="ltr">

```bash
git --version
flutter --version
java -version
javac -version
flutter config --jdk-dir "$JAVA_HOME"
flutter config --android-sdk "$ANDROID_HOME"
sdkmanager --sdk_root="$ANDROID_HOME" --licenses
sdkmanager --sdk_root="$ANDROID_HOME" "platform-tools" "platforms;android-36" "build-tools;36.0.0"
flutter doctor --android-licenses
flutter doctor -v
adb version
```

</div>

برای شبیه‌ساز Linux پشتیبانی مجازی‌سازی و KVM لازم است؛ [راهنمای رسمی شتاب‌دهی](https://developer.android.com/studio/run/emulator-acceleration) را دنبال کنید. در Linux اتصال USB ممکن است به گروه کاربری و قواعد udev سازنده نیاز داشته باشد؛ [راهنمای رسمی اتصال دستگاه](https://developer.android.com/studio/run/device) را بخوانید. در macOS معمولاً درایور USB جدا لازم نیست. ابزارهای سیستم را فقط با مدیر بسته یا نصب‌کننده نصب کنید؛ ساخت Flutter را با sudo اجرا نکنید.

## دریافت پروژه از Git و آماده‌سازی

### ۱. گرفتن یک نسخهٔ کامل

در ویندوز، PowerShell را باز کنید:

<div dir="ltr">

```powershell
New-Item -ItemType Directory -Force C:\dev | Out-Null
Set-Location C:\dev
git clone https://github.com/iarash84/PlanAct.git
Set-Location .\PlanAct
git status
git branch --show-current
```

</div>

در لینوکس/macOS، در پوشه‌ای قابل‌نوشتن مانند پوشهٔ شخصی، Terminal را باز کنید:

<div dir="ltr">

```bash
mkdir -p development
cd development
git clone https://github.com/iarash84/PlanAct.git
cd PlanAct
git status
git branch --show-current
```

</div>

فرمان clone فقط بار اول لازم است. اگر پوشه از قبل وجود دارد، دوباره در همان محل clone نکنید؛ وارد نسخهٔ موجود شوید و بخش همگام‌سازی انتهای سند را بخوانید. برای اولین دریافت عمومی نیازی به تنظیم نام و ایمیل Git نیست؛ این اطلاعات هنگام ثبت تغییرات لازم می‌شود. اگر Git ورود خواست، دسترسی مخزن/حساب را بررسی کنید؛ رمز حساب GitHub برای احراز هویت Git قابل اتکا نیست و باید از روش رسمی ورود یا توکن محدود استفاده کنید. اطلاعات ورود را در URL یا فایل پروژه ذخیره نکنید.

نشانهٔ درست‌بودن پوشه: [تعریف پروژه](../pubspec.yaml)، [فایل قفل وابستگی‌ها](../pubspec.lock)، پوشهٔ [کد برنامه](../lib/) و پوشهٔ [اندروید](../android/) در همان سطح‌اند. پوشهٔ [وابستگی‌های محلی](../third_party/) هم باید کامل دریافت شده باشد؛ آن را حذف یا با بسته‌های آنلاین جایگزین نکنید. برای شروع دانلود ZIP به‌جای Git پیشنهاد نمی‌شود، چون تاریخچه و فرمان‌های همگام‌سازی این راهنما را نخواهید داشت.

### ۲. دریافت وابستگی‌ها

از اینجا به بعد، مگر خلافش گفته شود، فرمان‌ها در **ریشهٔ مخزن** اجرا می‌شوند:

<div dir="ltr">

```text
flutter pub get --enforce-lockfile
flutter gen-l10n
dart run tool/generate_persian_copy.dart --check
dart run tool/generate_iranian_holidays.dart --check
```

</div>

فرمان اول بسته‌ها را مطابق فایل قفل دریافت می‌کند؛ فرمان دوم منابع محلی‌سازی را تولید می‌کند و دو فرمان آخر سازگاری خروجی‌های تولیدشدهٔ مخزن را می‌سنجند. هر فرمان باید بدون خطا تمام شود. خطای فایل قفل را با پاک‌کردن آن یا ارتقای جمعی بسته‌ها حل نکنید؛ ابتدا نسخهٔ Flutter و کامل‌بودن دریافت مخزن را بررسی کنید.

برای **ساخت نسخهٔ موجود** معمولاً نیازی به اجرای تولیدکنندهٔ پایگاه داده نیست. فقط اگر عمداً مدل/جدول مربوط را تغییر داده‌اید، طبق قواعد مهاجرت و آزمون‌های مخزن از تولیدکننده استفاده کنید؛ اجرای آن درمان عمومی هر خطای ساخت نیست. پوشهٔ اندروید را هم با ساختن یک پروژهٔ Flutter تازه جایگزین نکنید.

### ۳. بازکردن در ویرایشگر، در صورت نیاز

- **Android Studio:** گزینهٔ Open را بزنید و پوشهٔ اصلی PlanAct را انتخاب کنید، نه فقط پوشهٔ اندروید. مسیر Flutter SDK را در صورت درخواست معرفی کنید. در پنجرهٔ Terminal پایین IDE فرمان‌های همین سند قابل اجراست؛ نوع شل آن را بررسی کنید. پیام Gradle Sync را با اولین فرمان Flutter از ریشهٔ پروژه دنبال کنید تا تنظیمات محلی SDK ساخته شود.
- **VS Code:** از **File → Open Folder** پوشهٔ اصلی را باز کنید، افزونهٔ Flutter را نصب و مسیر SDK را معرفی کنید. فقط به مخزنی که منبع آن را می‌شناسید Workspace Trust بدهید. ترمینال داخلی از **Terminal → New Terminal** باز می‌شود.
- **بدون ویرایشگر:** همان PowerShell یا Terminal کافی است؛ مراحل ساخت یکسان‌اند.

## ساخت اولین فایل نصب؛ بدون کلید انتشار

برای جلوگیری از برخورد با نسخهٔ شخصی یا رسمی برنامه، اولین ساخت را با **شناسهٔ آزمایشی جداگانه** انجام دهید. این گزینه فقط روی ساخت Debug اثر دارد و اطلاعات نسخهٔ عادی را به نسخهٔ آزمایشی منتقل نمی‌کند.

ویندوز:

<div dir="ltr">

```powershell
$env:PLANACT_ISOLATED_VERIFICATION = 'true'
flutter build apk --debug
```

</div>

لینوکس/macOS:

<div dir="ltr">

```bash
export PLANACT_ISOLATED_VERIFICATION=true
flutter build apk --debug
```

</div>

ساخت اول Flutter، Gradle و ابزارهای بومی ممکن است چندین دقیقه یا بیشتر طول بکشد. تا پایان فرمان صبر کنید؛ گوشی یا Emulator لازم نیست. خروجی موفق معمولاً با پیام ساخته‌شدن APK و مسیر فایل تمام می‌شود. فایل خروجی: [APK آزمایشی](../build/app/outputs/flutter-apk/app-debug.apk). این فایل پس از ساخت روی رایانهٔ شما وجود دارد و در مخزن نگهداری نمی‌شود.

این ساخت از کلید Debug محلی استفاده می‌کند، برای استفادهٔ آزمایشی است و کلید رسمی انتشار نمی‌خواهد. شناسهٔ بسته در این حالت **com.iarash.planact.verification** و شناسهٔ عادی **com.iarash.planact** است. متغیر فوق در ترمینال فعلی می‌ماند؛ اگر ترمینال تازه باز کردید، برای ساخت/اجرای جداگانه دوباره آن را تنظیم کنید.

برای بازگشت به ساخت Debug با شناسهٔ عادی، فقط در صورت نیاز و با توجه به خطر برخورد با نصب قبلی، مقدار موقت را حذف کنید:

<div dir="ltr">

```powershell
Remove-Item Env:PLANACT_ISOLATED_VERIFICATION -ErrorAction SilentlyContinue
```

```bash
unset PLANACT_ISOLATED_VERIFICATION
```

</div>

**ساخت فایل به معنی آزموده‌شدن قابلیت‌های بومی نیست.** اعلان، آلارم، پیامک، قفل برنامه و بازیابی پشتیبان به شواهد دستگاه و پذیرش مستقل خود نیاز دارند. برای آزمایش اولیه از دادهٔ ساختگی استفاده کنید.

<a id="run-app"></a>

## اجرای برنامه روی گوشی یا شبیه‌ساز

### روش اول: گوشی واقعی، با یا بدون Android Studio

۱. ترجیحاً از گوشی آزمایشی استفاده کنید. برای اولین اجرا نیازی به پیامک بانکی واقعی یا اعطای همهٔ مجوزها ندارید.
۲. در تنظیمات گوشی، در About phone معمولاً هفت بار روی **Build number** بزنید تا Developer options فعال شود؛ محل دقیق بسته به سازنده فرق دارد. سپس **USB debugging** را فعال کنید.
۳. با کابل **قابل انتقال داده** وصل کنید، گوشی را باز نگه دارید و پیام اعتماد به کلید RSA همین رایانه را فقط در صورت شناخت رایانه تأیید کنید. در صورت نیاز حالت USB را به File transfer تغییر دهید.
۴. در ویندوز اگر دستگاه شناسایی نشد، درایور رسمی سازنده را نصب و Device Manager را بررسی کنید. در رایانهٔ عمومی گزینهٔ اعتماد دائمی را فعال نکنید.
۵. از ریشهٔ پروژه اجرا کنید:

<div dir="ltr">

```text
adb devices
flutter devices
```

</div>

باید دستگاهی با وضعیت **device** ببینید؛ **unauthorized** یعنی تأیید روی گوشی انجام نشده و **offline** یعنی ارتباط آماده نیست. شناسهٔ دستگاه را از خروجی Flutter بردارید. در همان ترمینالی که متغیر ساخت آزمایشی را تنظیم کرده‌اید، فرمان زیر را اجرا کنید؛ **DEVICE_ID** را با شناسهٔ واقعی جایگزین کنید:

<div dir="ltr">

```text
flutter run --debug -d DEVICE_ID
```

</div>

برنامه نصب و باز می‌شود. در ترمینال اجرای Flutter، کلید r بازخوانی سریع تغییرات سازگار، R راه‌اندازی مجدد و q پایان اجرای متصل را انجام می‌دهد. تغییر کد بومی یا بعضی تنظیمات به توقف و اجرای مجدد نیاز دارد. پس از کار، USB debugging را در صورت بی‌نیازی خاموش و اعتماد رایانه‌های نامطمئن را لغو کنید.

اگر فقط می‌خواهید APK ساخته‌شده را نصب کنید و از قبل دستگاه را آماده کرده‌اید، از ریشهٔ پروژه:

<div dir="ltr">

```text
adb -s DEVICE_ID install -r build/app/outputs/flutter-apk/app-debug.apk
```

</div>

در اینجا نیز شناسه را جایگزین کنید. می‌توانید APK را به گوشی منتقل و با فایل‌منیجر باز کنید؛ در صورت نیاز فقط برای همان منبع اجازهٔ نصب برنامهٔ ناشناس بدهید و پس از نصب آن اجازه را بردارید. محدودیت امنیتی دستگاه سازمانی را دور نزنید.

### روش دوم: شبیه‌ساز با Android Studio

در **Tools → Device Manager → Create Device** یک گوشی مجازی بسازید. یک System Image سازگار با معماری میزبان دریافت کنید؛ روی Apple Silicon معمولاً ARM64 و روی ویندوز/Linux x64 معمولاً x86_64. API 36 برای این راهنما انتخاب مناسبی است. دستگاه را روشن کنید و تا نمایش کامل صفحهٔ اصلی صبر کنید؛ سپس با دو فرمان فهرست دستگاه و اجرای Flutter در بالا ادامه دهید. در Android Studio می‌توانید دستگاه را از نوار ابزار انتخاب و Run را هم بزنید، اما برای **ساخت جداگانهٔ آزمایشی** مطمئن شوید فرایند IDE متغیر مربوط را دریافت کرده است؛ مسیر ترمینال صریح‌تر است.

اگر شبیه‌ساز باز نمی‌شود، مجازی‌سازی پردازنده باید در BIOS/UEFI فعال و شتاب‌دهندهٔ سازگار سیستم طبق [راهنمای رسمی](https://developer.android.com/studio/run/emulator-acceleration) نصب باشد. در ویندوز از مسیر توصیه‌شدهٔ فعلی Android Emulator و Windows Hypervisor Platform استفاده کنید؛ نصب HAXM قدیمی راه‌حل پیش‌فرض این راهنما نیست. تغییر امکانات ویندوز ممکن است راه‌اندازی مجدد بخواهد. استفاده از گوشی واقعی جایگزین ساده‌تری است.

### روش سوم: شبیه‌ساز بدون Android Studio، اختیاری

برای **نمونهٔ ویندوز x64** زیر، ابتدا ابزار Emulator و تصویر x86_64 را نصب کنید. این تصویر را روی میزبان ARM اجرا نکنید؛ تصویر باید برای معماری/سیستم‌عامل شما واقعاً در فهرست SDK موجود باشد:

<div dir="ltr">

```powershell
sdkmanager.bat --sdk_root="$env:ANDROID_HOME" "emulator" "system-images;android-36;google_apis;x86_64"
avdmanager.bat create avd --name PlanAct_API_36 --package "system-images;android-36;google_apis;x86_64" --device "pixel_6"
& "$env:ANDROID_HOME\emulator\emulator.exe" -avd PlanAct_API_36
```

</div>

اگر دربارهٔ ساخت پروفایل سفارشی سخت‌افزار پرسید، برای این نمونه **no** پاسخ دهید. اگر شناسهٔ سخت‌افزار موجود نبود، با فرمان زیر شناسه‌های نصب خود را ببینید و یکی را جایگزین کنید:

<div dir="ltr">

```powershell
avdmanager.bat list device
```

</div>

فرمان اجرای Emulator ممکن است ترمینال را مشغول نگه دارد؛ برای اجرای Flutter یک ترمینال دیگر باز کنید، وارد ریشهٔ پروژه شوید و متغیر ساخت جداگانه را دوباره تنظیم کنید. در لینوکس/macOS نام ابزارها بدون پسوند bat است و فایل Emulator در زیرپوشهٔ emulator داخل SDK قرار دارد؛ در macOS ARM64 تصویر موجود arm64-v8a را به‌جای x86_64 انتخاب کنید. ابزار خط فرمان نیازی به اجرای دائمی Android Studio ندارد.

<a id="local-release"></a>

## ساخت امضاشدهٔ محلی؛ فقط پس از اولین ساخت موفق

برای آزمایش اولیه، همان Debug کافی است. این بخش برای کسی است که آگاهانه فایل Release محلی می‌خواهد؛ **انتشار رسمی پروژه مسیر جداگانهٔ انتهای سند است**. کلید شخصی شما امکان به‌روزرسانی نصب رسمی با امضای نگه‌دارنده را نمی‌دهد. نسخهٔ Release این پروژه شناسهٔ عادی دارد؛ روی دستگاه دارای دادهٔ واقعی با آن آزمایش نکنید و برای رفع خطای امضا نسخهٔ قبلی را بی‌پشتیبان حذف نکنید.

### ۱. ایجاد کلید شخصی خارج از مخزن

در ویندوز، از JDK نصب‌شده استفاده کنید. اگر فایل هم‌نام قبلاً دارید، آن را بازنویسی نکنید:

<div dir="ltr">

```powershell
New-Item -ItemType Directory -Force C:\PlanActKeys | Out-Null
keytool -genkeypair -v -keystore C:\PlanActKeys\planact-local.jks -storetype JKS -alias planact-local -keyalg RSA -keysize 2048 -validity 10000
```

</div>

به پرسش‌های نام و مشخصات گواهی پاسخ دهید، هنگام تأیید مشخصات yes بزنید و رمز قوی انتخاب کنید. برای ساده‌شدن مدیریت، در پرسش رمز کلید می‌توانید همان رمز مخزن کلید را انتخاب کنید. رمز را داخل فرمان تایپ نکنید تا در تاریخچه نماند. فایل کلید و رمزهایش را امن و جدا از مخزن پشتیبان بگیرید؛ گم‌شدن کلید می‌تواند امکان به‌روزرسانی نصب‌های امضاشده با آن را از بین ببرد.

در لینوکس/macOS همان فرمان keytool با یک **مسیر مطلق شخصی خارج از مخزن** اجرا می‌شود؛ ابتدا پوشهٔ مقصد را بسازید و مسیر ویندوز را جایگزین کنید. ابزار keytool همراه JDK است، نه دانلود جداگانه.

### ۲. معرفی کلید به پروژه

با ویرایشگر یک فایل [تنظیمات امضای محلی](../android/key.properties) بسازید؛ نام آن نباید پسوند اضافی txt داشته باشد. چهار خط زیر نمونه‌اند و باید مقادیرشان را با اطلاعات واقعی کلید شخصی جایگزین کنید:

<div dir="ltr">

```properties
storeFile=C:/PlanActKeys/planact-local.jks
storePassword=REPLACE_WITH_YOUR_STORE_PASSWORD
keyAlias=planact-local
keyPassword=REPLACE_WITH_YOUR_KEY_PASSWORD
```

</div>

در ویندوز برای مسیر از اسلش رو به جلو مانند مثال استفاده کنید. در Linux/macOS مسیر مطلق خود را وارد کنید. این فایل حاوی رمز متنی است؛ از آن عکس نگیرید، منتشر نکنید و در گیت ثبت نکنید. پروژه آن را نادیده می‌گیرد، اما مسئولیت حفاظت از نسخه‌های کپی با شماست. اگر رمز شامل نویسه‌های ویژهٔ قالب Java Properties مثل بک‌اسلش است، باید مطابق همان قالب escape شود؛ رمز را برای دورزدن قالب ضعیف نکنید.

جایگزین این فایل، چهار متغیر محیطی **ANDROID_KEYSTORE_PATH**، **ANDROID_KEYSTORE_PASSWORD**، **ANDROID_KEY_ALIAS** و **ANDROID_KEY_PASSWORD** است. مقادیر غیرخالی محیطی بر فایل اولویت دارند؛ اگر امضای غیرمنتظره دیدید، محیط ترمینال را هم بررسی کنید. برای مبتدی، فایل محلی ساده‌تر است؛ رمز واقعی را در نمونهٔ فرمان قابل ثبت در تاریخچه ننویسید.

### ۳. ساخت و پیداکردن خروجی

از ریشهٔ پروژه:

<div dir="ltr">

```text
flutter build apk --release
flutter build appbundle --release
```

</div>

هرکدام مستقل‌اند؛ اگر فقط فایل نصب لازم دارید، فرمان اول کافی است. خروجی‌ها: [APK انتشار محلی](../build/app/outputs/flutter-apk/app-release.apk) و [بستهٔ AAB](../build/app/outputs/bundle/release/app-release.aab). نسخهٔ برنامه به‌طور پیش‌فرض از [تعریف پروژه](../pubspec.yaml) می‌آید. بدون پیکربندی امضا، ساخت Release عمداً متوقف می‌شود؛ پروژه نباید مخفیانه به کلید Debug برگردد. متغیر عبور از الزام امضا را برای حل این خطا فعال نکنید.

| Timeout، خطای TLS یا دریافت Maven/Gradle/Dart | اول دسترسی شبکه، ساعت سیستم و پراکسی رسمی ابزار مربوط را بررسی کنید؛ خاموش‌کردن TLS یا تغییر مخزن به منبع ناشناس راه‌حل امن نیست. |

اگر احتمال می‌دهید خروجی موقت ساخت خراب شده، ابتدا کارهای در حال ساخت را متوقف کنید و **فقط در ریشهٔ همین پروژه** اجرا کنید:

<div dir="ltr">

```text

```

</div>

این کار خروجی موقت ساخت پروژه را بازسازی می‌کند و قرار نیست اطلاعات برنامهٔ نصب‌شده را پاک کند؛ جایگزین تشخیص خطای شبکه، نسخه یا امضا نیست. برای حفظ جداسازی، متغیر ساخت آزمایشی را پیش از آن تنظیم کنید. کش سراسری، پایگاه داده، فایل قفل، کلیدها یا اطلاعات گوشی را بی‌دلیل حذف نکنید. نصب دوباره یا پاک‌کردن دادهٔ برنامه می‌تواند اطلاعات شخصی و کلیدهای وابسته به نصب را از دسترس خارج کند.

برای درخواست کمک، شناسهٔ ثبت فعلی را با فرمان زیر بگیرید و به‌همراه سیستم‌عامل، فرمان ناموفق، نسخهٔ ابزار و **اولین خطای واقعی** گزارش کنید:

<div dir="ltr">

```text
git rev-parse HEAD
flutter doctor -v
```

</div>

پیش از ارسال خروجی، مسیرهای حاوی نام شخصی، شناسهٔ دستگاه، مشخصات حساب، پیامک، یادداشت‌ها، رمز و اطلاعات کلید را حذف یا پوشانده کنید. فایل کامل تنظیمات امضا یا خروجی حساس برنامه را منتشر نکنید.

## چک‌لیست پایان راه‌اندازی

- [ ] نسخهٔ Git چاپ می‌شود و Flutter همان نسخهٔ مرجع است.
- [ ] Java و javac نسخهٔ 17 هستند و Flutter همان JDK را استفاده می‌کند.
- [ ] Android toolchain سالم است؛ هشدار ابزارهای پلتفرم‌های نامرتبط مانع این مسیر نیست.
- [ ] وابستگی‌ها مطابق فایل قفل دریافت و منابع محلی‌سازی تولید شده‌اند.
- [ ] ساخت Debug موفق و APK در مسیر گفته‌شده موجود است.
- [ ] اگر اجرا هم هدف بوده، دستگاه درست انتخاب و برنامه با شناسهٔ آزمایشی باز شده است.
- [ ] هیچ کلید، رمز یا دادهٔ شخصی وارد Git نشده است.

این چک‌لیست فقط **آماده‌بودن محیط و ساخت محلی** را نشان می‌دهد، نه موفقیت کل آزمون‌ها یا آمادگی انتشار. مسیرهای نصب این راهنما باید روی محیط پاک هر سیستم‌عامل جداگانه آزموده شوند؛ تطبیق با تنظیمات مخزن جای شاهد نصب از صفر نیست.

[<span dir="ltr">PRD</span>](product/PRD.md) رفتار و آمادگی محصول و [<span dir="ltr">AGENTS</span>](../AGENTS.md) قواعد پیاده‌سازی را مشخص می‌کنند. پیش از تغییر معنادار، قرارداد کوتاه را در همان درخواست ادغام یا سند ارزیابی موجود ثبت و به‌روز کنید؛ سند موازی نسازید:

- موفقیت قابل مشاهده، خطا، لغو، تلاش مجدد و اصلاح/بازگردانی؛
- دادهٔ پایدار و آثار راه‌اندازی مجدد، مهاجرت، پشتیبان/بازگردانی و پلتفرم؛
- مصرف‌کنندگان نیازمند بازخوانی و شاهد لازم برای هر ادعا.

مسیر اقدام کاربر ← فرمان ← قاعدهٔ دامنه ← نوشتن پایدار ← بازخوانی رابط ← مصرف‌کنندگان را دنبال کنید. کوچک‌ترین مسیر کامل مصوب را تحویل دهید. کار زیرساختی، قابلیت آمادهٔ کاربر نیست؛ پیش‌نیاز یا تصمیم نامشخص را اختراع نکنید و وضعیت ناقص را گزارش کنید. برای تغییر مستندات، سازگاری/اختلاف/پیوند کافی است؛ بازآرایی بدون تغییر رفتار به آزمون مرتبط نیاز دارد. این تناسب شرط امنیتی انتشار یا حفظ داده را حذف نمی‌کند.

پیش از ادغام، بازبین مستقل قرارداد، شواهد و مثال نقض را بررسی می‌کند. خودبازبینی جای بررسی مستقل نیست؛ عامل بازبین نیز مجوز انتشار مستقل نمی‌دهد. درخواست زیرساختی/ناقص تنها با ثبت محدودیت، مسئول و تصمیم عرضه قابل ادغام است و تضمین ضروری همان تغییر باید برقرار باشد. پذیرش درخواست مجوز انتشار کل برنامه نیست؛ مسئول انتشار همهٔ مسیرهای در دسترس و شرط‌های مشترک انتشار را بررسی می‌کند.

| معیار | شاهد و محیط | نتیجه | کمبود و تصمیم |
| --- | --- | --- | --- |
| نتیجهٔ قرارداد | دستور/مراحل، شناسهٔ ثبت و ساخت، تاریخ، دستگاه/سیستم‌عامل/حجم | موفق، ناموفق یا اجرا‌نشده؛ پیوند شاهد | مسئول، اقدام بعدی و تصمیم عرضه/انتشار |

شواهد تاریخی حذف نمی‌شوند؛ اعتبار آن‌ها برای نسخهٔ فعلی مشخص شود. گزارش پایان، پیاده‌سازی، راستی‌آزمایی، اجرا‌نشده‌ها و موانع انتشار را جدا می‌کند؛ نام بازبین و دامنهٔ پذیرفته‌شده ثبت شود.

آزمون دامنه محاسبه را ثابت می‌کند؛ ماندگاری به مخزن تولیدی و بستن و بازکردن دوبارهٔ پایگاه داده، رابط به مسیر ورود واقعی و بازخوانی و ادعای بومی به دستگاه نیاز دارد. شناسهٔ بسته، نسخه، نوع ساخت و تفاوت فایل آزمایشی/انتشار ثبت شوند. برای حجم/چیدمان، دادهٔ واقعی، بودجهٔ دستگاه مرجع، عرض باریک، متن بزرگ، راست‌به‌چپ و حالت‌های روشن و تیره بررسی شوند. رفع نقص مهم باید آزمون جلوگیری از تکرار خطا و یادداشت کوتاه معیار جاافتاده داشته باشد و به بازآرایی نامرتبط تبدیل نشود.

## نگهداری گزارش‌ها

خلاصه، دستور، محیط، تاریخ، شناسهٔ ثبت/ساخت و کمبود را در رکورد همان قابلیت نگه دارید. گزارش محلی در <span dir="ltr">`build/verification/`</span> است؛ خروجی خام همهٔ اجراها لازم نیست وارد گیت شود. ایجاد پوشه/هدایت خروجی اختیاری است و اسکریپت بررسی را تغییر نمی‌دهد.

برای <span dir="ltr">GitHub Actions</span> شناسهٔ اجرا/ثبت و گزارش/بستهٔ خروجی همان اجرا را ثبت کنید؛ انقضای بسته به معنی شاهد دائمی نیست. [شواهد تاریخی منتخب](verification/evidence/README.md) بازنویسی نمی‌شوند. شاهد خام جدید هدف مشخص، هویت اجرا و بررسی محتوای حساس می‌خواهد. گزارش موردارجاع هنگام پاک‌سازی بدون تغییر محتوا منتقل و پیوند اصلاح می‌شود؛ فقط خروجی موقت بی‌ارجاع حذف می‌شود. پیکربندی ساخت و فایل هش/منشأ انتشار گزارش موقت نیستند.

## بررسی محلی

پیش‌نیاز فعلی: <span dir="ltr">Flutter</span> <span dir="ltr">`3.47.5`</span>، <span dir="ltr">Dart</span> مطابق <span dir="ltr">`pubspec.yaml`</span>، <span dir="ltr">Java</span> <span dir="ltr">`17`</span> و <span dir="ltr">compile SDK</span> اندروید <span dir="ltr">`36`</span>.

### ویندوز

از ریشهٔ مخزن:

<div dir="ltr">

```powershell
.\tool\ci.ps1
```

</div>

اگر سیاست <span dir="ltr">PowerShell</span> مانع است، تغییر فقط برای همین فرایند:

<div dir="ltr">

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tool\ci.ps1
```

</div>

یا <span dir="ltr">PowerShell</span> 7:

<div dir="ltr">

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File .\tool\ci.ps1
```

</div>

برای بررسی بدون ساخت اندروید، مقدار قبلی متغیر را حفظ و سپس بازگردانید:

<div dir="ltr">

```powershell
$previousSkipAndroidBuild = $env:PLANACT_SKIP_ANDROID_BUILD
try {
    $env:PLANACT_SKIP_ANDROID_BUILD = 'true'
    .\tool\ci.ps1
} finally {
    if ($null -eq $previousSkipAndroidBuild) {
        Remove-Item Env:PLANACT_SKIP_ANDROID_BUILD -ErrorAction SilentlyContinue
    } else {
        $env:PLANACT_SKIP_ANDROID_BUILD = $previousSkipAndroidBuild
    }
}
```

</div>

این مسیر <span dir="ltr">CI</span> کامل نیست. اجرای کامل به امضای معتبر در <span dir="ltr">`android/key.properties`</span> یا متغیرهای <span dir="ltr">`ANDROID_KEYSTORE_PATH`</span>، <span dir="ltr">`ANDROID_KEYSTORE_PASSWORD`</span>، <span dir="ltr">`ANDROID_KEY_ALIAS`</span> و <span dir="ltr">`ANDROID_KEY_PASSWORD`</span> نیاز دارد؛ دستور اصلی را بدون <span dir="ltr">`PLANACT_SKIP_ANDROID_BUILD`</span> اجرا کنید.

## <span dir="ltr">CI</span> و رفع شکست

<span dir="ltr">GitHub Actions</span> برای درخواست‌های مقصد <span dir="ltr">`master`</span> و ارسال‌های <span dir="ltr">`master`</span> اجرا می‌شود؛ اجرای قدیمی همان شاخه/درخواست لغو می‌شود. مراحل شامل وابستگی، منابع تولیدشده، قالب‌بندی، تحلیل، کل آزمون‌ها و ساخت سازگار انتشار اندروید است.

۱. گزارش همان مرحله را بخوانید و علت را اصلاح کنید.
۲. اسکریپت متناسب با سیستم‌عامل را محلی اجرا کنید.
۳. خطای موقت زیرساخت/شبکه را با گزینهٔ <span dir="ltr">`Re-run failed jobs`</span> تکرار کنید؛ ثبت بی‌معنی نسازید.
۴. اثر تغییر فایل قفل، مهاجرت یا امضا را در درخواست ادغام بنویسید.

## انتشار اندروید

سلامت فنی و آمادگی محصول دو دروازهٔ مستقل‌اند. موفقیت <span dir="ltr">CI</span> پذیرش محصول نیست؛ دامنهٔ انتشار همهٔ قابلیت‌های در دسترس و موانع قبلی را شامل می‌شود. پنهان‌کردن ورودی، دروازهٔ مشترک امنیت/ماندگاری/پلتفرم را معاف نمی‌کند.

طبق تصمیم نگه‌دارندهٔ تنها در <span dir="ltr">۲۰۲۶-۱۰-۱۳</span>، اجرای دستی مجوز خودکارسازی «ساخت نامزد انتشار ← بررسی فنی ← انتشار همان فایل‌ها بدون ساخت مجدد» است؛ محیط انتشار یا تأیید نفر دوم لازم نیست. این تصمیم شاهد مستقل یا دستگاه را انجام‌شده نمی‌کند. [گردش کار انتشار](../.github/workflows/release.yml) فایل‌ها، هش‌ها و هویت ثبت/اجرا را به بستهٔ کاندید می‌فرستد؛ پس از بررسی فنی همان فایل‌ها و برچسب متصل به همان ثبت منتشر می‌شوند.

خودکارسازی آمادگی محصول را اعمال نمی‌کند؛ مسئولیت با نگه‌دارنده است. معیار الزامی ناموفق/اجرا‌نشده یا مانع امنیت/داده/پلتفرم اجازهٔ ادعای آمادگی یا انتشار دامنهٔ متأثر نمی‌دهد. ناقص‌بودن نیازمند تصمیم عرضه و محدودیت روشن است؛ برچسب آزمایشی جای تضمین ضروری را نمی‌گیرد.

انتشار فقط از <span dir="ltr">`master`</span> و اجرای دستی **<span dir="ltr">Release Android</span>**:

1. نسخهٔ <span dir="ltr">`X.Y.Z+build`</span> را در <span dir="ltr">`pubspec.yaml`</span> تغییر و در <span dir="ltr">`master`</span> ادغام کنید؛ شواهد پذیرش را به ثبت ثابت و فایل کاندید متصل کنید.
2. در <span dir="ltr">GitHub</span> مسیر <span dir="ltr">`Actions → Release Android → Run workflow`</span> را باز کنید.
3. نسخه بدون <span dir="ltr">`v`</span> مانند <span dir="ltr">`0.2.0`</span> وارد شود؛ پس از موفقیت بررسی‌ها انتشار خودکار است.
4. نسخه و یادداشت متناسب بررسی، اعتبارسنجی مشترک اجرا و کلید تولید فقط در مرحلهٔ ساخت آماده می‌شود. <span dir="ltr">APK</span> امضاشده از نظر شناسهٔ بسته، نسخه، معماری و گواهی بررسی می‌شود.
5. هویت و هش دوباره بررسی و همان فایل بدون ساخت مجدد منتشر می‌شود؛ شکست مانع انتشار است. لغو پس از درخواست ایجاد انتشار ممکن است آن را باقی بگذارد؛ پیش از تلاش مجدد وضعیت را بررسی کنید. نسخهٔ موجود بازنویسی نمی‌شود.
6. ثبت، شناسهٔ اجرا، کد نسخه، گواهی و هش <span dir="ltr">APK</span> همراه شاهد دستگاه نگه داشته شود. کد نسخهٔ انتشار از شمارهٔ اجرای گردش کار است و باید از همهٔ <span dir="ltr">APK</span>های توزیع‌شده بیشتر باشد.

برچسب را دستی نسازید/ارسال نکنید. کلید خصوصی، مخزن کلید و <span dir="ltr">`android/key.properties`</span> وارد گیت نمی‌شوند. نسخهٔ هدف <span dir="ltr">`0.2.7+18`</span> و [یادداشت نسخه](releases/0.2.7.md) است؛ یادداشت با هش در کاندید می‌ماند و متن انتشار را تأمین می‌کند. آماده‌سازی فایل‌ها مجوز اجرای گردش کار یا ادعای آمادگی نیست.

## تنظیمات دستی <span dir="ltr">GitHub</span>

نگه‌دارنده باید حفاظت شاخه/قواعد <span dir="ltr">`master`</span>، بررسی <span dir="ltr">CI</span> الزامی، درخواست ادغام و حل گفت‌وگوها، محدودیت ارسال مستقیم و ادغام فشرده را در تنظیمات فعال کند. برای نگه‌دارندهٔ تنها بازبینی نفر دوم شرط فنی نیست؛ مسئولیت پذیرش باقی است. اجرای انتشار فقط برای افراد مورداعتماد و مقادیر محرمانه در <span dir="ltr">`Settings → Secrets and variables → Actions`</span> مخزن باشد؛ گردش کار به مقادیر مخصوص محیط انتشار دسترسی ندارد. فایل‌های مخزن اعمال خودکار این تنظیمات را ادعا نمی‌کنند.

## همگام‌سازی و بازگشت

پیش از کار جدید:

<div dir="ltr">

```bash
git fetch origin
git switch master
git pull --ff-only origin master
git switch -c feature/short-description
```

</div>

پیش از درخواست ادغام:

<div dir="ltr">

```bash
git fetch origin
git rebase origin/master
```

</div>

اگر تغییر ثبت‌نشده دارید، پیش از همگام‌سازی توقف کنید و با دیدن وضعیت Git، فایل‌ها را آگاهانه ثبت یا در محل امن نگه دارید؛ فرمان حذف اجباری تغییرات راه‌حل عمومی نیست. اگر rebase تعارض داشت و روش حل آن را نمی‌دانید، با فرمان زیر به وضعیت پیش از شروع همان rebase برگردید و کمک بگیرید:

<div dir="ltr">

```text
git rebase --abort
```

</div>

سپس اسکریپت محلی بالا را اجرا کنید. برای اولین ثبت تغییرات باید هویت Git را تنظیم کنید؛ این هویت رمز ورود نیست و ایمیل ممکن است در تاریخچه عمومی شود. نمونه‌ها را با نام و ایمیل مناسب خود، یا ایمیل خصوصی ارائه‌شده توسط GitHub، جایگزین کنید:

<div dir="ltr">

```text
git config user.name "Your Name"
git config user.email "YOUR_EMAIL"
git status
git diff
```

</div>

پس از بازبینی، فقط فایل‌های مربوط را با فرمان افزودن Git انتخاب و ثبت کنید؛ برای جلوگیری از ثبت ناخواستهٔ اطلاعات حساس، همهٔ فایل‌ها را کورکورانه اضافه نکنید. نمونهٔ زیر فقط برای تغییر همین مستند است:

<div dir="ltr">

```text
git add docs/development-workflow.md
git commit -m "docs: improve development setup guide"
git push -u origin HEAD
```

</div>

این ارسال نیازمند دسترسی نوشتن به مخزن مقصد است. اگر مشارکت‌کنندهٔ بیرونی هستید، ابتدا در GitHub یک Fork شخصی بسازید و نسخهٔ Fork را clone کنید؛ مقصد درخواست ادغام همچنان شاخهٔ اصلی مخزن PlanAct است. در GitHub پس از push، گزینهٔ **Compare & pull request** را باز کنید، مقصد و شاخهٔ مبدأ را بررسی و هدف، آزمون‌ها و محدودیت‌ها را بنویسید. اگر شاخه قبلاً ارسال شده و rebase تاریخچهٔ آن را تغییر داده است، push عادی ممکن است رد شود؛ بدون هماهنگی و بررسی مالکیت شاخه از ارسال اجباری استفاده نکنید.

تغییر منتشرنشده را در همان شاخه اصلاح کنید؛ تاریخچه، دفتر مالی، رخداد حل‌شده و پشتیبان را برای ساده‌سازی حذف نکنید.

</div>
