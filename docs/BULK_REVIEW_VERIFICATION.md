## Relationship remainder queue — acceptance contract (before implementation)

Existing income/expense transactions are prerequisites, not network or SMS permission. Finance bulk work is separate; Inbox files and the existing Inbox section are untouched.

Trace: queue read → finance entries and transactional RelationshipReviewRepository.loadReview → domain remainder/independent projection → visible page selection (maximum 50) → Persian exact-count/current-page confirmation → relationship-specific sequential runner → existing decideReview fresh durable transactional requireExpected/append → per-row progress and reread → Today refresh and existing detail reopening. Review tokens retain amount, active/history fingerprints, revision and decision identity. Allocation or newer review changes reject stale confirmation/retry/Undo, rather than implicitly approve fresh data.

Success: only eligible unreversed income/expense positive unreviewed remainders can be selected, including partially allocated transactions. Individual or displayed-page selection never means all filtered results. Search/type/page changes clear selection. Navigation/confirmation cancellation writes nothing. Partial successes remain committed; failures retain original tokens and require another explicit confirmation; stop applies between items. Browsing and unrelated detail actions remain available. Existing explicit per-item reopening is recovery; no bulk financial confirmation, deletion, reversal, allocation or match modification.

Durability: reuse append-only review history and existing personal-backup preservation, with no schema, dependency or persisted batch. Restart rereads durable state, with empty selection and fresh user confirmation. Balances, entries, allocations and prior history must remain unchanged. A failed item cannot roll back earlier successes or prevent later items. Replay of stale tokens cannot duplicate decisions.

Evidence required: high-volume page/filter and invalid eligibility cases; production transactional allocation staleness, middle SQL failure, replay, old Undo/new decision, file cold reopen/history/balance preservation; widget count/scope/cancel/progress/retry/filter/detail journeys and route discovery; focused regression tests, format and analyzer. ## Inbox safe multi-selection bulk reject — acceptance contract

Entry: Inbox with existing local pending/edited suggestions. No SMS permission or financial account is required to reject. Select individual eligible rows or all eligible rows in the displayed bounded page (maximum 50), never all filtered results. Bank/status/order/page changes clear selection. Refresh drops changed revisions instead of silently selecting newer snapshots. Confirmation names scope and exact count; cancelling it writes nothing.

Trace: Inbox selection → Inbox-specific application runner → InboxUseCases.reject → AtomicInboxReview.reviewAtomically → fresh transactional status/revision comparison and append-only per-item history → committed-row removal and Inbox reload → existing rejected-filter reopen. No financial bulk confirmation, ledger mutation, batch persistence, schema/dependency or Finance/relationship changes.

Success/failure: sequential independent item transactions; visible attempted/success/failure counts, active-row pending, cancellation before the next item (not rollback of an in-flight commit). No whole-UI lock: other rows and browsing remain available. Failure retry uses original snapshots and reconfirms count; stale snapshots fail rather than overwrite newer edit/reject/reopen/confirmation. Successful rows are not retried. Existing explicit per-item reopen is recovery, not financial reversal; no stale bulk Undo.

Durability: decisions survive cold file reopen and source replay. Selection/progress are intentionally temporary, never resumed after restart. Existing metadata/backup history is reused without new stored fields. Interrupted runs retain committed items only; user rereads fresh state and selects again.

Evidence required: focused widget journeys for page/count/cancel/progress/retry/filter scope; production repository cold reopen/replay/stale history and financial-state preservation; format/analyzer/regressions. Shared Material theme/tokens, Persian labels/numbers, RTL and wrapping controls. Coverage: Inbox header/cards/dialog migrated; single-item editor/confirmation/reopen intentionally unchanged; other surfaces unaffected. Existing eager Inbox reads remain a limitation: selection/display page is bounded, not database query memory.

Before implementation: contract recorded. Independent review/native accessibility/reference-device performance are parent/release-owner gates. Exposure: bounded current-mission development work, not release readiness. Parent owns coordinated product-contract updates; this slice does not edit AGENTS/PRD.
